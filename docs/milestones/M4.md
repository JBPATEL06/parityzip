# M4 - Verify and Repair

Branch: `m4-verify-repair` from `main` (M3 merged and tagged `m3`). Read `docs/PROJECT.md`, the project rules, and the skills `par2-7z-cli-wrapper`, `flutter-linux-desktop`, `yaru-ui-guidelines`, `milestone-verification`.

## Scope
Make the **Verify** and **Repair** tabs work. The user picks a `.par2` file; the app checks the protected files in that folder and, on the Repair tab, repairs them. Format-independent: it must work for any file protected by par2 (7z today).

### 0. Spikes first (before any feature code)
On scratch data under `/tmp` (use the M3 output on `random_10MB.bin` at 10%, plus a 7z archive from the app), write findings to `docs/spikes/par2-verify-repair.md` with real captured output for each case, including exit code:
1. Clean set: `par2 verify`.
2. One damaged byte (`dd ... seek=1000 conv=notrunc`): verify, then repair. Paste full outputs.
3. Damage beyond the redundancy (overwrite about 40% of a 10MB file when only 10% recovery data exists): verify exit code and message; then run repair and note what happens to the file (untouched or modified?).
4. Archive missing from the folder.
5. Archive truncated (`truncate -s -1000`) and archive with extra bytes appended.
6. Main `.par2` file deleted but `.volNNN+NN.par2` files present; and a `.vol` file used as the input argument.
7. Repair details: where does the original damaged file go (backup name/location), what does the repaired file look like, and does the final state verify OK? Does repair write in place or to a new file then rename? Is a partial state possible if the process is killed mid-repair? (Test by killing it on the 500MB file if available.)
8. Verify output lines: which lines are stable enough to parse for per-file status (found / damaged / missing) and for block counts (recovery blocks available vs needed)? Paste the lines. If the format looks unstable, say so.
9. Progress output samples for verify and repair (`\r` use, wording before the percent).
10. Exit codes seen in each case above, next to the skill's table. Report any difference.
Stop and report if any result contradicts the `par2-7z-cli-wrapper` skill. Do not guess.

### 1. Core logic (pure Dart, unit tested)
- `Par2Service.buildVerifyArgs` and `buildRepairArgs` (name-only arguments, `./` prefix for names starting with `-`, `workingDirectory` = the `.par2` file's folder).
- Exit-code mapper to states: `ok`, `damagedRepairable`, `damagedNotRepairable`, `insufficientData` (spike code 4 and similar), `error`.
- Verify output parser: best-effort per-file status and block counts, only for lines the spike showed to be stable. If parsing fails, the state still comes from the exit code and the raw log is shown. Parsing failure is never an error.
- Input validation: file exists, has extension `.par2` (case-insensitive), is a regular file.
- Repair pipeline using exit codes only: (a) verify; if `ok` -> finish with "Nothing to repair"; if `damagedRepairable` -> (b) repair; then (c) verify again; if `damagedNotRepairable` or other -> stop with a clear explanation and do NOT run repair. The final verify in (c) is the proof of success: if it is not `ok`, report failure.

### 2. Safety and cancel rules
- Never delete any file. Never delete the backup of the damaged file that par2 creates; show where it is and its size after repair.
- Before repair, if the spike says repair writes new data and keeps a backup, show an info line with the needed free space in the folder if it can be estimated, otherwise a generic note.
- Cancel during verify: kill the process, no side effects.
- Cancel during repair: show a confirmation dialog ("Stopping now may leave the file partly repaired. A backup of the damaged file is kept.") and, if confirmed, kill the process and show the state of the files per the spike (what exists on disk now).

### 3. UI
Per `yaru-ui-guidelines`. **Verify tab:** drop zone / "Choose .par2 file" (`file_selector`, extension filter) accepting any file of the set (`.par2` or `.volNNN+NN.par2`), shows the protected folder, button "Verify", progress card with Cancel, result card with one of: OK (check icon), Damaged but repairable, Damaged and cannot be repaired, Recovery data incomplete, Error; each result has one sentence on what to do next, optional per-file list (if parsed), "Open folder", "Copy report". When the result is "Damaged but repairable", show a button "Go to Repair" that switches tab with the same file preselected. **Repair tab:** same input; button "Repair"; shows the pipeline steps ("Checking", "Repairing", "Checking again"); result card: Repaired and verified / Nothing to repair / Cannot be repaired / Error; after repair shows the backup file location. If `par2` is missing, both tabs show the banner and are disabled. Wrong file type (not `.par2`) is rejected with a clear message.

## Out of scope
Creating recovery data for existing files, encryption (M5), ZIP output, extraction, packaging.
